# components/

Presentational and feature components for the public site. Flat layout — no feature subdirectories, except for one special case (`OptimisticSortOrder/`) that needs a server/client split.

## Layout

```
components/
├── CustomPortableText.tsx     ← The portable text renderer — extend this to handle new block types
├── Header.tsx                 ← Shared page/project header (title + portable-text description)
├── HomePage.tsx               ← Interim Salt hero (approved copy; full section build pending)
├── ImageBox.tsx               ← Wrapper around next/image for Sanity images
├── Navbar.tsx                 ← Top navigation; reads from settings singleton
├── ProjectListItem.tsx        ← A project card in the showcase list
├── TimelineItem.tsx           ← A single milestone within a timeline
├── TimelineSection.tsx        ← A timeline, embedded as a portable-text block
├── SaltWordmark.tsx           ← Inline SALT wordmark SVG (recolors via currentColor)
├── OptimisticSortOrder/       ← Feature folder — server wrapper + lazy client impl
│   ├── index.tsx              ← Server: checks draft mode, lazy-loads client version
│   └── index.client.tsx       ← Client: useOptimistic reordering for the Studio overlay
└── motion/                    ← GSAP/Lenis motion primitives (all 'use client')
    ├── gsap.ts                ← Central plugin registration + EASE/DURATION constants
    ├── LenisProvider.tsx      ← Smooth-scroll root, ScrollTrigger sync (mounted in (personal) layout)
    ├── PageTransition.tsx     ← Curtain wipe on internal navigation
    ├── LineReveal.tsx         ← SplitText line-mask reveal
    ├── WordSwap.tsx           ← Two-face hero word swap
    ├── ParallaxMedia.tsx      ← Scroll-scrubbed oversized media
    ├── ScrubSection.tsx       ← Scrubbed timeline over [data-scrub] children
    └── ClipReveal.tsx         ← clip-path wipe on scroll-in
```

### The `motion/` folder

The second sanctioned exception to the flat rule. All motion components are client components built on GSAP + Lenis. Rules:

- **Import gsap and plugins from `./gsap`** (`components/motion/gsap.ts`), never from `'gsap'` directly — registration happens once there, and `EASE`/`DURATION` mirror the CSS motion tokens in `app/globals.css`.
- **All GSAP work goes through `useGSAP`** from `@gsap/react` (React Compiler-safe, auto-cleanup). No DOM reads in render.
- **Every component checks `prefersReducedMotion()`** and renders static/visible content when it's on. Keep that invariant when adding patterns.
- New animations should be one of the named patterns in `DESIGN.md` Motion — no one-off effects.

## Conventions

### Flat layout — stay flat

**Don't** create feature subfolders like `components/projects/` or `components/layout/`. The codebase is small enough that the flat list is easier to scan. Names should be unique and descriptive enough to stand on their own.

**The one exception** is a component that legitimately needs both a server and a client file (see `OptimisticSortOrder/`). In that case, use a folder named after the component with `index.tsx` (server) + `index.client.tsx` (client).

### Named exports are the default

Most components export a named function:

```ts
export function Header(props: HeaderProps) { ... }
```

The one outlier is `ImageBox.tsx`, which uses a default export. New components should use named exports — matching the majority keeps imports consistent.

### Async server components are fine

`OptimisticSortOrder/index.tsx` is an `async` function. That's allowed in server components and is the right pattern when you need `await draftMode()` or to pass through data that's already been fetched upstream.

### Tailwind classes inline, template literals for conditionals

There is **no `cn()` / `clsx` / `classnames` utility** in this codebase. Don't import one. The convention is:

```tsx
// Static classes — write them inline
<div className="sticky top-0 z-10 flex flex-wrap items-center">

// Conditional classes — use a template literal with ternaries
<div className={`${centered ? 'text-center' : 'w-5/6 lg:w-3/5'}`}>

// Mixed — static + conditional in one string
<Link className={`text-lg hover:text-black md:text-xl ${
  menuItem?._type === 'home' ? 'font-extrabold text-black' : 'text-gray-600'
}`}>
```

`package.json` lists `classnames` as a dependency but nothing actually imports it — it's either a transitive or leftover. Don't add new uses of it.

Prettier sorts Tailwind classes automatically via `prettier-plugin-tailwindcss`, so don't worry about class order.

## Types: generated vs hand-written

There are two sources of types in play:

- **`@/sanity.types`** — generated by `npm run typegen` (i.e. `sanity schema extract && sanity typegen generate`). Types here match the schema exactly. Imports look like `import type {HomePageQueryResult} from '@/sanity.types'`. Used in `HomePage.tsx`, `Navbar.tsx`.
- **`@/types`** — hand-written, lives in `types/index.ts`. Currently contains `MilestoneItem` and `ShowcaseProject`. These are narrower, cleaner versions of the generated types — useful when the generated shape is too wide for a specific use case. Used in `ProjectListItem.tsx`, `TimelineItem.tsx`.

**Rule of thumb:** use the generated type (`@/sanity.types`) wherever possible. Only reach for `@/types` when the generated type has too many optional fields and you want to assert narrower guarantees at the component boundary. If you add a new hand-written type, put it in `types/index.ts` — don't scatter ad-hoc types across component files.

Never hand-edit `sanity.types.ts` — it's regenerated by typegen.

## Visual editing: `createDataAttribute` and `data-sanity`

Components that emit `data-sanity` attributes: `Navbar.tsx`, `TimelineSection.tsx`. The pattern is:

```tsx
import {createDataAttribute} from 'next-sanity'
import {studioUrl} from '@/sanity/lib/api'

const dataAttribute = data?._id && data?._type
  ? createDataAttribute({
      baseUrl: studioUrl,
      id: data._id,
      type: data._type,
    })
  : null

// Then on elements — the argument is the path within the document:
<header data-sanity={dataAttribute?.('menuItems')}>
<Link data-sanity={dataAttribute?.(['menuItems', {_key: menuItem._key}])}>
<span data-sanity={dataAttribute?.('duration.start')}>
```

**When to add it:** when you want an editor to be able to click a rendered element in the Presentation tool and jump straight to that field in the Studio. This is useful for array items (so they can click a specific menu item) and for derived/formatted values (like a year computed from a datetime — stega won't handle those automatically).

**When not to:** most plain string fields are already editable inline via the client's stega integration. Don't add redundant `data-sanity` attributes where stega already covers it.

`createDataAttribute` can accept a `path` at creation time (see `TimelineSection.tsx`) or be called with a path argument each time. Both work; the per-call version is more flexible.

## `stegaClean` — stripping stega markers

`next-sanity` embeds editing markers in string fields when stega is enabled on the client (see `sanity/lib/client.ts`). Most of the time you want those markers present so the Presentation overlay can pick them up. But sometimes you need the **raw** string — for example:

- Using a string in a ternary condition
- Passing a value through a library that doesn't understand stega (e.g. `new Date(...)`)
- Rendering text inside a component that itself re-uses the string in a non-rendering way

For those cases, import `stegaClean` from `next-sanity`:

```ts
import {stegaClean} from 'next-sanity'

const cleanTitle = stegaClean(menuItem.title)
```

Examples in the code: `Navbar.tsx` (cleans menu item titles), `TimelineSection.tsx` (cleans timeline titles), `TimelineItem.tsx` receives already-cleaned milestones.

## The `OptimisticSortOrder/` split pattern

This is the reference for how to build a component with both server and client halves.

**Why the split:** the optimistic reordering only matters when an editor is reordering items inside the Sanity Studio Presentation tool. In production for an end user, it would just be dead weight in the bundle. So we:

1. Render a server component that takes the same props (`OptimisticSortOrder/index.tsx`)
2. If we're not in draft mode, the server component short-circuits and just returns `children` directly
3. If we ARE in draft mode, it lazy-loads the client implementation with `lazy(() => import('./index.client'))` wrapped in `<Suspense>`
4. The client implementation (`OptimisticSortOrder/index.client.tsx`) has `'use client'` and uses `useOptimistic` from `next-sanity/hooks`

**The public import is `import {OptimisticSortOrder} from '@/components/OptimisticSortOrder'`** — consumers import from the folder, which resolves to `index.tsx` (the server wrapper). They should never import `index.client.tsx` directly.

**When to use this pattern for a new component:**

- The client behavior is only relevant in draft mode or Studio contexts
- You want the production bundle to exclude the client code entirely
- The component wraps children rather than rendering its own structure

**When NOT to use this pattern:** any component that always needs to be client-side. Just mark the whole file `'use client'` and leave it there. Don't split for the sake of splitting.

## `CustomPortableText.tsx` — the extension point for rich content

All portable text on the site flows through `CustomPortableText`. The `components` prop passed to `next-sanity`'s `PortableText` maps:

- **`block.normal`** — plain paragraphs, with a configurable `paragraphClasses` prop for callers to pass Tailwind classes
- **`marks.link`** — the `link` annotation used in body content
- **`types.image`** — inline images (with caption + alt)
- **`types.timeline`** — embedded timeline sections, delegated to `<TimelineSection />`

**To handle a new portable-text block type or annotation:**

1. Add it to the schema in `sanity/schemas/` (e.g. a new `defineArrayMember` inside a `body` field)
2. Re-run `npm run typegen`
3. Add a handler to the `components` object in `CustomPortableText.tsx`

**Do not create a new portable-text renderer elsewhere.** Having one renderer means styling and behavior stay consistent across pages.

## `ImageBox.tsx` — the Sanity image wrapper

All Sanity-sourced images should go through `ImageBox`:

```tsx
<ImageBox
  image={project.coverImage}
  alt={`Cover image for ${project.title}`}
  classesWrapper="relative aspect-[16/9]"
/>
```

It internally calls `urlForImage(image)` from `sanity/lib/utils.ts`, which builds a Sanity CDN URL with `auto('format').fit('max')` applied. Then it passes the URL to `next/image`.

**Defaults:** width 3500, height 2000, size `100vw`. Override for thumbnails (see `TimelineItem.tsx` which passes `width={65} height={65}`).

**Gotcha:** the component takes a `data-sanity` prop via rest-destructured props, but typed explicitly in the interface. If you need to add more pass-through attributes, add them to the interface explicitly — don't rely on a spread.

## Things to verify before adding a new component

1. Does it actually need to be a component, or can the JSX live inline where it's used?
2. Is it a named export (matching the rest of the codebase)?
3. If it has client behavior, is `'use client'` the whole-file solution, or does it warrant the `OptimisticSortOrder/` split pattern?
4. If it takes Sanity data, is the type from `@/sanity.types` (generated) or does it need a cleaner hand-written type in `@/types`?
5. If it renders portable text, are you extending `CustomPortableText` rather than writing a new renderer?
6. If it displays Sanity images, are you going through `ImageBox`?
7. If it should be inline-editable in the Presentation tool, does it emit the right `data-sanity` attributes?
8. Classes inline with template literals — no `cn()` imports.
